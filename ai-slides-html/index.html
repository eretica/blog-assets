01エンジニアの認識を覆す

エンジニアの仕事とは

  1. システム全体を理解し、活用方法を考える
  2. チームと連携・コミュニケーションを大切にする
  3. 問題を見つけ、改善を繰り返す
  4. 技術やツールのトレンドを学び続ける
  5. 価値を生み出す

02できるエンジニア像

できるエンジニアとは

スキルだけでなく「姿勢と行動」が評価される

  2. チームと協力して成果を出せる
  3. 適切なコミュニケーションで信頼を築ける
  4. 自分の担当と影響範囲を理解し、責任を持てる

03成長の姿勢

成長とは

「受け身」ではなく、自分から学びにいく姿勢が成長を加速させる。

成長には振り返りが欠かせない

  • 「やったことは最適だったか？ 他に良い方法は？」と考える
  • ときには「この進め方、逆に失敗しそう…？」と疑う視点も必要

フィードバックは待つだけでは得られない

  • 自分から聞きに行く姿勢が大事
  • PRにコメントがない時でも、「もっと良いやり方あるかも？」と考える習慣を持とう

03成長の姿勢

わからないままはダメ

“わからない”は成長の出発点。黙るより、聞くほうが信頼される。

危険：わかったふり

わからないことをそのままにする人（わかったふり）は「嘘をつく人」と同じくらい危険。信用を失う

信頼につながる：早めに質問

「わからない」は素直に認め、早めに質問することが信頼につながる。質問はマイナス評価ではなく、プラス評価になる

ミーティングで内容が理解できないときは

  • その場で質問
  • その場で調べる
  • 直後に確認

03成長の姿勢

その不安、本当に気にするべき？

「聞いていいのかな？」と思ったら、聞いていいサイン

「先生と生徒」に置き換えるとわかりやすい

生徒聞いていいのかな？
迷惑じゃないかな？
先生「そんなの聞いてくれればいいのに」

わからないことを放置されたり、嘘をつかれたりする方がずっと困る

  • “自分には大ごと”でも、他人から見れば大したことないかもしれない
  • 自分の視点だけで考えすぎると、行動に移せなくなることがある
  • 実際は、「そんなに気にしなくていいのに」というケースがほとんど
  • 一度、自分を俯瞰して見る習慣を持とう。自分の視点に囚われず、客観的に見る癖をつけよう
  • “気にしすぎ”を疑ってみるのも、行動力の一部。

  • そのアプローチのやり方を自身にどんどん貯めていく
  • 「前に似たケースがあったな」と気づけると、対応が速くなる
  • 他の人の作業や改善も意識することで、学びの幅が広がる

自分の経験＋他者の経験＝加速する成長

04アピールしよう（成果は見せてなんぼ）

アピール＝信頼構築の手段

報告は信用、可視化は武器。アピールは誠実さの表れ。

アピールがないと

  • フルリモートでは特に見えづらく、誤解されやすい
  • 「何してるか分からない」と思われてしまう
  • 頑張っているのに、何もしてないという評価になるのは勿体無い

だから、伝える

  • アピールは信頼構築の手段。自分を守ることにもつながる
  • 進捗が出ない時ほど、進捗や背景を伝えることが重要に

04チームの中での動き方

なんでも即時対応

優先度は色々あるが、小さいタスクほど速攻で片付けよう

自分のために

  • 小さいタスクを抱えると、常に気になって集中できない
  • 小さいタスクは小さいからすぐ片付けられる

信頼のために

  • 即時対応すると、頼れる存在と認識されやすい
  • すぐやってくれる人は貴重。簡単なのに信頼・評価・チャンスを得やすい
またこの人に頼みたい。

04チームの中での動き方

他の人の動きを把握する

他者の動きに目を向けることで、視野が広がり、成長のヒントが得られる。見渡す力も身につけよう

  • 他の人が何をしているかを知ることで、システム全体の理解が深まる
  • 他の人の進行状況を知っていれば、適切な人に質問・相談ができる
  • 「この前〇〇やってたよね？」という情報が、意外な場面で役に立つ
  • 自分のタスクに直接関係なくても、関心を持つことがチーム力につながる

  • 必要に応じて関係者と意図をすり合わせる行動も忘れずに

05問題への向き合い方

担当箇所を見極めよう本当に修正すべきなのはどこなのか？

「とりあえずこっちで直しておく」は、将来的な負債になり得る

  • 指摘された内容が、自分のプロジェクトや担当範囲に属しているとは限らない
  • 実は、別のチーム・プロジェクト・システム側の対応が正しいケースもある
  • 無理にこちらで修正すると、責任があいまいになったり、逆に不整合を生むことがある
  • 「一見こちらの問題に見えるが、本当にそうか？」というスコープの見極めが重要
  • 必要なら、範囲の切り分けや関係者への確認を行う習慣を持とう

05問題への向き合い方

「やる」と「やらない」を判断できるように

“やる”より、“やらない判断”がプロの仕事

  • 実はやらなくていいことは意外と多い
  • タスクも「本当に必要か？」「削れないか？」を考えるクセをつけよう
  • “やらない判断”は、プロジェクトを守る判断でもある
  • システムの構造や優先順位を理解しているからこそ、削る判断ができる
  • 削る力こそ、プロジェクトを健全に保つ技術。価値のある選択を

06裁量と与信

裁量をとりに行こうチャンスを掴め

裁量は「振られるもの」でもあるが、「取りに行くもの」でもある。
挑戦が、成長と裁量を引き寄せる。

取りに行く

  • 今の仕事に満足して止まっていては成長できない
  • やれることをどんどん広げることで、自分の市場価値も上がる
  • 「ワクワクする」「興味ある」レベルの動機で十分。みんな最初は未経験

ただし

  • 勝手に導入を始めるのはNG。報連相は必須
  • 属人化はリスク。チーム全体で触れる状態を意識しよう
  • 「この人なら大丈夫そう」という与信は必要

06裁量と与信

与信を確保する

与信とは、「この人なら任せても大丈夫そう」と思われる信頼感のこと

どうやって得るか

  1. 成果を出せる人
    タスク処理や速度だけでなく、価値を生む人
  2. できない・わからないことを正直に伝えられる誠実な人
  3. 状況を理解して、自律的に行動できる人
  4. 困ったときに状況を共有し、相談できる人

06与信を確保する

一人で抱え込むと、チャンスが遠ざかる

  1. 一人で抱え込む
  2. 周囲は不安になる
  3. 次の依頼をためらう
  4. 「負荷をかけたくない」と思われる
  5. チャンスが遠ざかる

だから、困ったときは状況を共有し、相談する

信頼は、コードの外側で築かれる。
安心して任せられることも強さ

07技術的な習慣

テストやCIは、“信頼されるコード”を書くために必要な習慣

✕ テストやCIの目的ではない「壊れないようにする」ため
→
◯ テストやCIの目的「壊れてもすぐに気づける」ため
  • 自分も、他人も、意図せず壊すことはある。だから守る仕組みが必要
  • テストがあることで、安心して変更し、進化させられる
  • 「このコードはこう動くべき」という自分の意思表示でもある
  • AIも仕様を誤認・勝手に変える時代だからこそ、検証手段としてのテストは欠かせない
  • 感覚がつかめないうちは、テストは多めでもいい。やりながら身につく
  • テストが落ちたらNG。でも仕様が変わったなら、テストを変えるのも正しい判断

CIとテストがあってこそ、安心して挑戦できる。

07技術的な習慣

効率のカギは、“道具の使い方”にある

知らないまま使い続けるのは、時間を捨ててるのと同じ。効率の差は、気づきの差。

  • 初学者のうちは、ツールの最低限の機能で使いがち
  • でも実は、ちょっとした理解で何倍も効率よく使えるものが多い
  • 気づかないまま時間をムダにしていても、自分では気づけないことがほとんど

08情報のアップデート

アップデートしない自分は、古くなる

現状維持＝価値が下がっていく時代。学びを止めれば、気づかぬうちに置いていかれる

閉じた環境では、得られる情報に限界がある

  • オフィスやプロジェクトの中だけでは、技術やトレンドの変化に気づけない
  • 情報収集は、一度やればいいものではなく、継続する習慣

08アップデートしない自分は、古くなる

まるで「弥生時代の日本」と「戦国時代の中国」のように

日本が農耕を始めた頃、中国では鉄器・戦術・国家統治が進化していた

同じ時間を過ごしていても、情報の差で“時代の差”がつく

08情報のアップデート

情報をキャッチする方法

情報の差は、行動の差。拾う人だけが先に進める。

  • SNSエンジニア界隈の動き
  • 外部のエンジニアと話す / 登壇を聞くリアルな現場の知見
  • npm trendsライブラリの人気・流行
  • Googleトレンド話題の移り変わり
  • GitHubスター数、issue、更新頻度から活発度を確認

トレンド＝すぐ使う必要はない

業務では枯れた技術が基本。でも「選べる判断軸」は持っておくべき。

09要望の本質を聞き出す

相手の言葉をそのまま受け取るな

表面的な要望＝本当に必要なこと、とは限らない

  • 相手の発言は、理想やイメージの断片にすぎないことが多い
  • 希望通りに作っても、目的や前提とズレて失敗するケースは珍しくない
  • 大切なのは、ヒアリングを通じて“本音”や“本質的なゴール”を引き出すこと

09相手の言葉をそのまま受け取るな

例：夢の庭 vs 現実

要望（夢）「草木のある素敵な庭にしたい」
でも
実際には…
現実
  • 虫が嫌いで窓が開けられない
  • 雑草の手入れが追いつかず、放置されてしまう
  • 結果、理想だったはずの庭がストレスの原因に

“夢”を叶えるつもりが、現実は“失敗”になるケースもある

09相手の言葉をそのまま受け取るな

「本当に必要なものは何か？」を一緒に考える

  • ときには「それはやめた方がいいかもしれません」と提案を返す勇気も必要
  • ただし、否定するだけでなく、なぜそう考えるかの背景を丁寧に伝える

正しく聞いて、正しく疑う。それが本当の信頼につながる。

10マインドセット

常に課題を感じ、改善する意識を

タスクをこなすだけでは、成長も価値も生まれない。
課題に気づける人だけが、価値を積み上げられる。

その“違和感”を放置しない

なんか使いづらいこのコード、読みにくい
  • 自分や他人が使っていてつらいと感じる部分は、すでに課題のサイン
  • 「過去の歴史があるから…」「誰かが作ったから仕方ない」→ そんな遠慮はいらない

改善のタイミングも“戦略的”に

  • 改善が早すぎると、逆に効率を下げるリスクもある
  • ベストな改善方法が見えるまで、一時的に“負債”を許容する判断もアリ
  • 重要なのは、「現状を正しく認識した上で、いつどこから手をつけるか」を考えること

10マインドセット

ミスっても死なない。やり直しは成長の証

重要じゃない「失敗しない」
→
ずっと大事「失敗から立て直せる」
  • かならず“正解”を選べなくてもいい。最初から完璧な選択なんて、ほとんどできない
  • やってみないと分からないことのほうが圧倒的に多い
  • 実行して、失敗したと感じたら、また挑戦するだけ
  • 失敗したら、「なぜうまくいかなかったか」がわかる。失敗から得られる経験は大きい
  • 気づきと改善があるなら、それはすでに前進
  • 失敗を恐れて止まるほうが、成長の機会を逃している
  • チームやシステムは、試行錯誤が前提で作られている
  • だからこそ、まずは動いてみることが求められる

10マインドセット

発想力と想像力を鍛える

発想力・想像力は、エンジニアにとって重要な武器。考えるクセが、引き出しを増やす。

なぜ武器になるのか

  • タスクを受けたときに「どんな改修が必要か」「どこに影響が出るか」を考えられる力
  • 解決の方法は一つではない。最適な手段を選べるかどうかが問われる

経験と好奇心で鍛えられる

  • 普段使っているサービスや仕組みに「どう作ってるのか？」と興味を持つだけでも十分
  • 日常のモノやアプリを「自分ならどう設計するか」と考えるクセをつける

知識も発想の材料になる

  • 書籍・ブログ・他人のコードを通じて、引き出しを増やしておこう
  • 実際に使わなくても「こういうやり方もある」と知っているだけで強みになる

10マインドセット

文化は作る物。変える物

組織の文化は「与えられるもの」ではなく、「自分たちでつくるもの」

  • 技術的な成果だけでなく、働き方や関わり方も文化を形づくる
  • 一人の行動・言葉・姿勢が、文化を変えるきっかけになる

現状を鵜呑みにしないことが大切

  • 「なんとなく続いていること」こそ、見直す価値がある
  • 不要な習慣や空気に気づけることが、最初の一歩

より良い文化は、より良いチーム・環境を生み出す

  • 声を上げることが組織の改善につながる
  • 誰かの勇気が、全体を動かすこともある

11自己認識

自分の現在を自覚する

自分のエンジニアとしての現在地を把握しよう。
今できること、これからできるようにすべきことを見つめよう

能力が低い人ほど、自分を高く見積もりがちだ。
経験が浅ければ、自分のレベルすら正しく測れない

だからこそ、“自分を疑う視点”を持つ者が、成長を加速させる
